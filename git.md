# Git notes

## Основные концепции

* **Ветки (branches)** - параллельные версии проекта. Нужны для создания, переключения и слияния фичей без поломки основного кода.
* **Теги (tags)** - понятные метки для конкретных версий и релизов (например, `v1.0`, `v2.0`).
* **Markdown (.md)** - простой формат для оформления файлов `README.md`, документации и личных конспектов.

---

## 5 Главных команд

| Команда | Что делает на самом деле |
| :--- | :--- |
| `git init` | **Инициализировать репозиторий.** Создает скрытую папку `.git` и делает текущую директорию проектом Git. |
| `git add` | **Добавить файлы в индекс.** Готовит выбранные файлы или изменения к следующему коммиту. |
| `git commit` | **Зафиксировать изменения.** Делает снимок (сохранение) всех подготовленных файлов с пояснением. |
| `git push` | **Отправить изменения.** Заливает твои локальные коммиты на удаленный сервер (GitHub/GitLab). |
| `git pull` | **Забрать изменения.** Скачивает и сразу вливает свежие изменения из удаленного репозитория к себе. |

---

## Расширенные команды

* `git checkout` - переключение между ветками или отмена изменений в файлах.
* `git merge` - слияние указанной ветки с текущей.
* `git rebase` - подтягивание коммитов поверх другой ветки (альтернатива merge для чистой истории).
* `git fetch` - скачивание всех обновлений с сервера без автослияния с локальным кодом.
* `git revert` - безопасная отмена коммита с созданием нового "отменяющего" коммита.
* `git diff` - просмотр разницы между файлами, коммитами или ветками.
* `git clone` - полное копирование удаленного репозитория к себе на ПК.

## Стратегии ветвления

> **Стратегия ветвления** - это правила, по которым ведётся разработка в Git. Она определяет, какие ветки живут всегда (например, `main` или `dev`), как правильно называть фиче-ветки, а также как и когда делать слияние веток.

### Популярные подходы:
1. **GitFlow** - классическая стратегия с множеством веток (`main`, `develop`, `feature/*`, `release/*`, `hotfix/*`). Отлично подходит для крупных проектов с редкими релизами.
2. **GitHub Flow** - максимально простая схема: есть ветка `main`, от неё создаются фиче-ветки, которые после проверки через Pull Request сразу сливаются обратно.
3. **GitLab Flow** - средний вариант с акцентом на окружения (`staging`, `production`).
4. **Trunk-Based** - современный подход для быстрого CI/CD: все разработчики коммитят прямо в одну главную ветку (`trunk`/`main`) частыми короткими итерациями.
